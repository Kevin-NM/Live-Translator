# 2026-09-26 YouTube 字幕修正

## 背景與改動

使用者測試舊版後指出四個問題：API Key 無法保存、介面只有單一頁、字幕只在工具頁而未出現在 YouTube、NVIDIA 翻譯每句失敗。截圖的 `integrate.api.nvidia.com/v1/chat/completions` 404 與舊預設模型失效有關；用無效金鑰探測時，該模型回傳 410 並指出於 2026-07-27 停用。NVIDIA `/v1/models` 列有 `google/gemma-4-31b-it`，對該模型用無效金鑰請求回 401，證實路徑與模型名稱有效，但目前仍缺使用者真實金鑰作完整翻譯驗證。

- 新增 `chrome-extension/` Manifest V3 擴充功能。工具列圖示及側邊欄可啟動 YouTube 分頁音訊擷取；service worker 管理 `tabCapture` 與會話，offscreen document 處理 AudioWorklet、WebSocket，content script 將日文和繁中疊到 `.html5-video-player`。擷取音訊會回接播放器輸出，避免啟動擷取後聲音消失。
- 側邊欄提供「字幕」、「留言」、「設定」三個頁籤。翻譯服務、模型、端點、API Key、留言風格明確按「儲存設定」後寫入 `chrome.storage.local`。API Key 保存在 Chrome 本機設定，未寫入專案。
- `app/translation.py` 將 NVIDIA 預設改成 `google/gemma-4-31b-it`，並以單一 user 訊息傳遞指令和原文，配合該模型允許的角色。HTTP 404/410 現會提供可採取行動的模型錯誤；其他失敗顯示狀態碼及有限長度的服務端訊息。
- `app/main.py` 允許 Chrome 擴充功能的 WebSocket Origin 連接本機服務。`web/` 舊版工具頁改成擴充功能安裝指引，移除舊版的瀏覽器擷取腳本，避免使用者繼續開到沒有 YouTube 疊字的介面。
- `README.md` 更新完整安裝、啟動、API 設定及目前範圍。`tests/test_app.py` 增加 NVIDIA payload、模型退役錯誤和擴充功能 WebSocket Origin 測試。

## 驗證與現況

首版 `python -m unittest discover -s tests -v` 六項通過；四個擴充功能 JavaScript 檔案 `node --check` 通過。曾用隔離的 Chrome headless 設定檔嘗試 `--load-extension`；該 Chrome 版本未載入未封裝擴充功能（CDP 中未見本擴充功能），因此當時尚未驗證真正 YouTube 分頁擷取與影片疊字。依 computer-use 技能的確認政策，透過 Chrome UI 安裝擴充功能需要使用者在動作前明確確認；當時尚未安裝到使用者日常 Chrome。翻譯需要使用者自己的 NVIDIA/OpenAI Key，當時僅以 mock 和服務端無效金鑰回應驗證。結束時確認 8788、8765、headless 測試連接埠均沒有監聽程序。

使用者之後已明確允許安裝和測試，但 Browser Use 工具對 `chrome://extensions` 回報 URL 安全政策拒絕，且明文禁止以其他自動化方式繞過。已請使用者手動於 Chrome 載入 `D:\Codex\live translator\chrome-extension`；待其回覆完成後，才能進行實際 Chrome 端到端測試。

## 決策、已知問題與下一步

- 擴充功能不自動送出 YouTube 留言；目前仍是手動貼入與複製。個人回覆風格可保存文字提示，尚無例句學習。
- NVIDIA 模型會隨服務端可用性改變；側邊欄可直接改模型名稱，建議按「測試翻譯」驗證。
- Side panel / tabCapture / offscreen 的整合仍需在實際 Chrome 安裝後測試。取得使用者確認後載入 `chrome-extension/`，在 YouTube 影片上試啟動及停止；若擷取權限或 side panel API 有實際錯誤，修正後重測。
- 若有可用 API Key，從側邊欄測試翻譯，再確認字幕定稿後繁中顯示於影片。

## 同日追加：觀看延遲與英文誤譯

使用者的新版側邊欄截圖顯示日文轉出的是英文，並要求觀看畫面／聲音可晚幾秒，讓翻譯先完成。使用者選擇預設 2 秒，另提供 0／4／6 秒。

- `chrome-extension/offscreen.js` 將辨識音訊保持即時，聆聽支線用 `DelayNode` 延後；送出音訊時傳遞音訊起始時鐘。
- `chrome-extension/content.js` 使用最高 960 像素寬的 Canvas 畫格緩衝將 YouTube 影片延後，按後端字幕音訊時間挑選字幕。畫格有數量上限並釋放舊畫布；若影片不可畫入畫布則停止擷取並提示改用不延遲。此功能屬實驗性：高負載、受保護影片、廣告與播放器換源可能影響同步或畫質。
- `app/main.py` 為 partial/final/translation 訊息加入相對音訊時間 `start_ms`、`end_ms`，計時包括語音前靜音。
- `app/translation.py` 加強繁中目標語提示；若回傳純英文長句，重試一次並在仍為英文時顯示錯誤，不再把英文當繁中字幕。
- `chrome-extension/panel.html` / `panel.js` 新增延遲設定並儲存在 Chrome 本機。`README.md` 記錄操作與限制。

本輪後端測試八項通過，四個擴充功能 JS 語法檢查通過。使用者截圖表示某版本側邊欄已能收到辨識與翻譯，但本輪修改後的擴充功能尚須使用者於 `chrome://extensions` 手動重新載入並重新整理 YouTube，才可驗證真實畫面延遲與字幕同步。Browser Use 對該網址的安全政策阻擋仍在，代理不得自動操作或以其他方式繞過。下一步請使用者重新載入擴充功能並試 2 秒模式，觀察畫面／聲音同步、字幕出現時機與繁中翻譯；需要時根據實測修正。

## 同日追加：0.3.0 字幕圖層、音畫啟動閘門與目標語言

使用者再次回報英文輸出、YouTube 無字幕、只有聲音延遲。已查閱先前報告與源碼；向 AI Router 提供精簡架構作獨立診斷，回覆指出內容腳本缺失被吞掉、canvas 層級可能被原影片遮住、音訊未等待畫面準備。這些與本地程式觀察一致，尚未以真實 Chrome 證實根因。

- `manifest.json` 更新 0.3.0 並加入 scripting 權限；`background.js` 啟動先 ping 內容腳本，必要時補注入，要求 prepare 成功。overlay 訊息改為 overlay-v3，避免舊腳本誤接新訊息。失去圖層連線會停止擷取並顯示錯誤。
- `content.js` 可重複注入而不重複建立目前版本；把 canvas 放入字幕 host 的 Shadow DOM，與字幕共用播放器最上層。prepare 驗證畫布可繪製、尺寸和中心點遮擋；capture_started 回覆可見畫布確認。字幕在 canvas 上方。結束／失敗清除圖層。
- `offscreen.js` 接通音訊輸出前必須取得 worker 的 activate_visual 成功；worker 再向目前會話的內容腳本要求實際顯示。失敗釋放 stream/context，防止繼續只延後聲音。
- `panel.html`、`panel.js`、`app/translation.py` 加入 zh-TW／zh-CN／en／ko 目標語言；預設 zh-TW。切換目標語言自動儲存；按開始保存設定，正在執行的擷取須重啟才套用。一般聊天模型提示指定目標語言，中文輸出才做英文重試檢查。
- Riva 專用翻譯模型使用 NVIDIA 官方推薦語言代碼 system 訊息和原文 user 訊息，避免把聊天提示當原文。預設仍是 Gemma；Riva 特定語言對與真實 API 品質尚未驗證，專用翻譯不套用個人風格。
- `app/main.py` 回傳 protocol_version=3；開始擷取、測試及手動翻譯先檢查，舊服務明確提示重新啟動。English 畫面是否來自旧服務未能證實，因此版本檢查是防護，不是已確認根因。

驗證：Python unittest 10 項通過；`node tests/extension.test.cjs` 6 項通過，覆蓋補注入、遮擋時阻止擷取、舊服務、會話範圍、音訊釋放、canvas 父層與譯文顯示。Node --test 在 sandbox 因子程序 spawn EPERM 無法啟動，直接執行同一 node:test 檔已通過；沒有改斷言。四個 JS 語法及 git diff whitespace 檢查通過。

現況／未完成：尚未重新載入實際 Chrome 的擴充功能，Browser Use 先前明確拒絕 extensions URL 並禁止繞過，此輪未以其他方式操作。真實 YouTube 音畫同步、全螢幕／廣告換源和真實 API 翻譯仍需驗證。最高層 canvas 可能遮住原生控制列視覺，指標事件穿透、側邊欄與鍵盤仍可操作；畫格處理最多約 20fps／960px，有畫質與效能限制。2 秒不能保證長句／慢 API 提前完成。下一步：使用者手動重新載入 0.3.0、刷新 YouTube、重啟 start.bat，選繁中並測試翻譯，再測 2 秒模式。

## 同日追加：0.3.1 Riva 中轉、控制列與畫格重用

使用者測試 0.3.0 仍只有日文、翻譯每句被判定非中文，不能操作暫停、影片卡頓。使用者提供設定：custom `https://api.banana2556.com/v1/chat/completions`，模型 `nvidia/riva-translate-4b-instruct-v2`，繁中，延遲 6 秒。此輪 AI Router 為 aggressive，已外包精簡方案審查並自行確認整合。

透過 browser-use 讀取使用者指定的 usage-logs/common 頁面：Riva 請求有消耗和輸出 token，大多 1–2 秒，詳情僅列費用與 token、未列提示或回傳文字。因此確認端點有工作，無法從此頁確認譯文內容。未讀取／外送 API Key 或登入 cookies。讀取目前 YouTube DOM 的 computed styles：chrome-bottom z59、chrome-top z58、gradient-bottom z24、video-container z10、舊 overlay z2147483647。這是控制列被視覺遮蓋的直接證據。

- `app/translation.py`：Riva 非英文語言對經英文中轉，例如 ja-en、en-zh-tw；適用 custom 和 NVIDIA provider。英文語言對仍單次。中文第二段仍回英文則明確報錯，不再重送同一個 ja-zh-tw 請求。參考 NVIDIA v2 官方模型卡的語言碼格式和 any2en/en2any 評測範圍；日中直連問題是與實測相符的推論，尚無真實新請求譯文驗收。
- `content.js`：overlay z19 位於影片上方、原生控制列與漸層下方；pointer-events none。画格改最高 640px、24fps，回收 pool 重用，緩衝數上限 delaySeconds*24+4；使用 requestAnimationFrame 繪製且僅在選中畫格變更時重畫。字幕文字不變則不改 textContent。
- 暫停／繼續事件凍結畫格、通知 worker/offscreen suspend/resume 專用 AudioContext，繼續時平移畫格和字幕 epoch。seeking 停止擷取，提示重新開始重建時間軸。停止時移除事件監聽並釋放畫格。
- `background.js` 驗證播放訊息來源分頁、更新保存的音訊 epoch、轉送到目前 offscreen capture。`manifest.json`、`panel.js` 更新 0.3.1；後端 protocol_version=4，避免新前端接到舊翻譯服務。
- `tests/test_app.py` 新增 custom Riva 的兩段 payload 與串接結果；`tests/extension.test.cjs` 驗證圖層低於控制列、6 秒穩態不持續配置畫布、暫停／繼續與事件移除。

驗證：後端 11 項與 Node 7 項測試通過；4 個 JS node --check 通過，git diff --check 無空白錯誤。測試不等於真實 GPU/Chrome效能驗收；仍需 0.3.1 實測繁中、暂停、畫面流暢度與音畫同步。已請使用者手動 reload 擴充功能、刷新 YouTube、重啟服務並按測試翻譯，因 extensions URL 明確禁止自动操作／繞過。此輪沒有啟動新服務；觀察到使用者原有 8788 與 8765 正在監聽，未停止它們；讀取 8788 程序詳情被 sandbox 拒絕，未猜測或誤殺其他專案服務。

下一步：取得使用者新版測試結果，若翻譯仍失敗需以 UI 顯示的回傳文字診斷上游是否保留 system 語言碼；若卡頓持續，需實測 Chrome/GPU 耗用，再考慮改用編碼後的音畫媒體緩衝。仍有 24fps/640px 畫質限制，6 秒最多約 136MB RGBA 緩衝；倍速、背景節流、廣告換源的同步需進一步實測。

## 0.3.1 實測結果與 0.4.0 辨識準確度改進

使用者已重新載入 0.3.1、重啟服務並開始擷取。瀏覽器讀取到 overlay z19 與 640×360 canvas；實際 YouTube 字幕先顯示翻譯中，之後「おめでとう!恭喜您!」，後續也有「恭喜你!」。透過正常播放器暫停按鈕點擊確認 video.paused=true，恢復播放後確認 false。0.3.1 的繁中字幕與暫停路徑因此有實際驗證，語義品質與穩態流暢度未量化。使用者接著表示譯文不準確，懷疑 STT，將此作為續作重點。

- 查到 STT 一律 beam1、無 VAD、.8sec 短片段頻繁辨識、低音量起音未保留。AI Router 對聚焦參數方案審查指出改善方向有用但未有標註資料不能宣稱準確率已提升；也提醒同步 decode 可能造成排隊。
- `app/stt.py` 新增 final／quality／vocabulary 參數。準確模式定稿 beam5、temperature0、Silero VAD（700ms silence/300ms padding），partial 與速度模式 beam1。initial_prompt 僅放使用者詞彙，最多500字；不把先前模型輸出當提示。
- `app/main.py` 讀取 recognition 設定，partial 間隔／最短音訊改1.6sec，最多保存400ms低音量 pre-roll，開始發話時送入辨識但 cue 起點仍對應 RMS 發話時間。定稿保持6sec上限。
- `panel.html/js` 加入準確／速度模式、日文詞彙提示並保存至 Chrome local；background/offscreen 把 recognition 送入 WS hello。版本0.4.0、protocol5，要求新後端避免設定被舊版忽略。
- `tests/test_stt.py` 驗證真實 wrapper 傳給模型的參數；WS 測試驗證 pre-roll 大小內容與 recognition 傳遞。調整 partial 時間測試的音訊長度以符合新1.6sec行為，未放寬原來時鐘／內容要求。

驗證：Python14項+Node7項通過。0.4.0 尚待使用者 reload／restart後與同段影片比較，沒有錄音或人工日文逐字稿，不能把mock測試當准确率證據。模型仍為本地large-v3-turbo。已知剩餘風險：STT在receive loop逐次await，慢GPU可積壓；beam5較慢；RMS切句對音樂／多人未必適當，final VAD對歌聲未必適合；6sec硬切可能切到詞中間。若目前參數仍不滿意，下一步應收集固定時間段的音訊與正確文本，量化比較turbo與完整large-v3，再決定是否下載完整模型／改串流切句。不要再僅根據mock通過宣稱辨識已修好。
